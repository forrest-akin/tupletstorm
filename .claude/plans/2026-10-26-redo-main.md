## Decoder error model

Settled before any decoder code; every commit keeps it.

- `pub fn decode(input: &str) -> Decoded`, `Decoded { pub score: Score, pub issues: Vec<Issue> }`.
  Total: no `Result`, no panic, for every `&str`. A `legacy: bool` field joins with old-link import.
- Expected failures are values. Parsers (`Bar::parse`, `Node::parse`, `Rat::from_str`, the
  `tc`/`ov` item parsers) return `Result<_, ParseError>`. `decode` is the single place that turns a
  `ParseError` into an `Issue` and substitutes what the reference substitutes (4/4 in 16ths for a
  bad bar, tempo 80, a dropped item, rests).
- `Issue` and `ParseError` are enums in `crates/rhythm-tree/src/issue.rs`, one variant per
  problem, each carrying the fields its message needs. `Display` prints the reference's wording
  byte for byte. `Issue::level()` is `Level::Error` for `BarReplaced` only, `Level::Warn` for every
  other variant. Variants are added in the commit that first produces them (listed per commit).
- Unexpected failures are broken internal invariants and panic with `expect("<invariant>")`. The
  only one: `Rat` arithmetic overflowing `i64`, which the limits rule out (denominators stay at or under
  8 · 64⁷ = 2⁴⁵ while depth ≤ 6, splits ≤ 64 and meter denominators ≤ 32; commit 9b extends the limits to grafted
  overrides). Nothing in the core catches a panic.
- Numbers in link text: a digit run parses as `u32`, saturating at `u32::MAX`; sums of parsed
  values are `u64`. No overflow is reachable, and a huge value reaches the range check and is
  reported with the saturated number (the reference prints a float; no fixture case covers it).
- Where the reference silently substitutes for malformed input and no fixture case pins it,
  `decode` reports a warn issue (CLAUDE.md: problems come back as issues). Each site and its
  message is in the commit that adds it.
- Issues come in the reference's order (ref:839-848): tempo, then bars, `tc`, `ov`, then every
  other field in first-appearance order, unknown fields and lanes in one loop. Each commit reports
  its keys at their place in that order.
- The shell: the wasm crate maps each `Issue` to `{ level: 'error' | 'warn', msg }` once, in
  `openLink`, and the client lists them. `Score::set_hit` returns `Result<(), EditError>`; the wasm
  crate throws its `Err` as `JsError`, because in the client it can only come from a bug, and
  nothing in the client catches it.
- `view` and `setHit` re-decode a canonical link and drop its issues: they were listed at open, and
  a canonical link re-decodes with at most the `custom lane … kept as-is` notice. One comment at
  that site says so.

## The client–core boundary

The client's state is the canonical link text. Every wasm call takes the link and decodes it; the
client never holds a `Score`. Decided, not raised: it has the fewest moving parts (no score object
crossing the boundary and back, so no re-validation, as the old `checked_score` needed; no wasm
handles to free; undo in milestone 3 is a stack of strings) and the link is the groove
(`docs/milestones.md`, phase 1). Its cost is a decode per call, measured in commits 5b and 9b.

Final shape at the end of this plan (each commit adds the fields it lists):

| wasm export (JS name) | Returns | First commit |
| --- | --- | --- |
| `openLink(input: string)` | `{ link: string, lanes: string[], issues: { level, msg }[] }` | 1 (`issues`), 3 (`lanes`), 5a (`link`) |
| `view(link: string, lanes: string[])` | `GrooveView` | 1 (no `lanes` argument until 3) |
| `setHit(link, lane, bar, leaf, letter)` | the new canonical link; throws `JsError` on an `EditError` | 5b |

```ts
type Rat = { num: number; den: number };
type Leaf = { segment: number; start: Rat; span: Rat };          // start: quarters from the top of the bar
type BarView = { meter: string; grouping: string | null; length: Rat; leaves: Leaf[] };
type LaneView = { id: string; name: string; letters: string; bars: { hits: string; leaves: Leaf[] }[] }; // leaves: 9b
type GrooveView = { title: string; tempo: number; bars: BarView[]; lanes: LaneView[] };
type Issue = { level: 'error' | 'warn'; msg: string };
type Core = {                                                    // members and fields arrive as in the table
  openLink(input: string): { link: string; lanes: string[]; issues: Issue[] };
  view(link: string, lanes: string[]): GrooveView;
  setHit(link: string, lane: string, bar: number, leaf: number, letter: string): string;
};
```

fragment or the query string. DTOs live in `crates/rhythm-tree-wasm/src/view.rs` as plain

`core.ts` over the real package in Vitest (after `initSync` with the `.wasm` bytes) so the mirror

## User decisions

All three wait for RFD 0004; recommendation first.

1. **Play's scheduler for milestone 2** (RFD 0004 undecided). Recommended: schedule one pass when
   Play is pressed (one `AudioContext`, one `AudioBufferSourceNode` per event, Stop closes the
   context); fewest parts, but no loop, and edits made while playing are heard on the next Play.
   Alternatives: a lookahead scheduler (a ~25 ms timer queueing ~100 ms ahead) that loops and hears
   edits within one window, at the cost of a timer, a cursor and recompiling on edit; or an
   AudioWorklet/Worker scheduler, immune to main-thread stalls but the most parts, which nothing in
   milestone 2 needs.
2. **Drum samples.** Recommended: a CC0 one-shot kit you choose, one sample per lane, accents and
   ghosts as gain, MP3 files in `web/public/samples/`; few files and licence-clean, but accents and
   ghosts are volume only. Alternatives: a sample per lane letter (truer articulations; about 40
   files to source and load); synthesised voices (no files or licences, but the sample-loading
   criterion would have nothing to load and needs rewording).
3. **Swing at playback.** Recommended: not applied in milestone 2 (`sw` round-trips but plays
   straight). Alternative: apply it to binary splits as Groove Scribe does, which needs a rule RFD
   0004 hasn't settled.
